# 消息列表方案：选型记录与性能基线（Task 0.2）

> **如实说明**：计划书 Task 0.2 要求「分别实现两个一次性原型」并对比后保留结论。
> 本项目**没有做原型对比**——直接实现了方案 B（下方）。这份文档记录的是
> **事后判断的依据与实测数字**，不是原型对比的结果。这个偏差记在台账里，
> 不假装 Task 0.2 已完全满足。

## 一、计划书给的两条路线

1. **QListView + 自定义 QAbstractListModel + Delegate**：虚拟化由 Qt 负责，
   撑得住任意条数，但**渲染能力受限于 delegate 的 `paint()`**。
2. **虚拟化消息容器**：每条可见消息用独立组件，保留完整组件能力，
   虚拟化需要自己做。

## 二、实际选择：方案 2 的具体形态

选了**「每条消息一个富文本组件 + 滞性化（只物化最近一页）」**，理由是按
本项目的真实需求排序的：

| 需求 | 方案 1（delegate 绘制） | 方案 2（独立组件 + 滞性化） |
| --- | --- | --- |
| Markdown 富文本（标题/列表/表格/代码块） | 要在 `paint()` 里手工排版或画 `QTextDocument` | `QTextBrowser` 原生支持 |
| 代码高亮、可选中、可复制文本 | delegate 里选区/复制要自己实现 | 原生支持 |
| 思考块「点击展开」 | 要自己做命中测试与状态 | 用一个按钮即可 |
| 工具步骤 chip 可点开 | 同上 | 同上 |
| 图片内嵌显示 | 要在 delegate 里解码绘制 | `QLabel` + pixmap |
| 2,000 条滚动 | 天然支持 | **需要滞性化**（已实现） |
| 分支切换 | 一次 setModel | 重建窗口（一页量级，可接受） |

**取舍的核心**：本项目每条消息都是**交互式富文本**（markdown + 可展开思考块 +
可展开工具步骤 + 图片），这些都是组件的强项、delegate 的弱项。
而那些能力用 delegate 实现，工作量与出错面都比「加一层滞性化」大得多。
所以：**选组件路线，用滞性化补上它的唯一短板**。

### 滞性化怎么做的

`ChatView.load_history()` 只物化**最近 `HISTORY_PAGE`（60）条**，
更早的折叠成顶部一个「加载更早的 N 条消息（还有 M 条）」入口，
点一次多放一页（`_load_earlier`）。数据早就在内存里，滞性化**只影响组件数量**。

## 三、实测性能基线（Task 10.2 采集）

本机（Windows 11 / 该开发机）实测，`tests/integration/test_long_session_pressure.py`：

| 场景 | 规模 | 实测 |
| --- | --- | --- |
| 构建压测库（写入 + 迁移） | 2,000 消息 + 20 分支 + 500 运行 + 12 压缩版本 | 0.089 s |
| 读主线会话（含逐条解密） | 2,000 条消息 | **0.036 s** |
| 会话列表（扫全部分支计数） | 20 分支 / 2,038 条 | 0.042 s |
| 历史搜索（解密后内存匹配） | 2,000 条 | 0.054 s |
| 请求日志装配 | 500 轮（意图 + 传输） | 0.025 s |

**关于字段级加密的成本**：最初担心「读 2,000 条要解约 6,000 次密」会成为瓶颈。
实测**不成立**——ChaCha20-Poly1305 对百字节级载荷吞吐极高，全量读取 36 ms。
真正需要留意的是**界面侧的物化数量**，那正是滞性化解决的。

**测试用例里不写死毫秒阈值**，只给宽松上限（5 s）断言「没有病态行为」，
同时把实测数字打印出来。理由：固定阈值在不同机器上只会变成随机失败。

## 四、这个选择已知的代价

- **重建成本**：切会话/改主题要重建当前窗口（≤60 个组件），不是 setModel 那种 O(1)。
  实测这在交互可接受范围内，但它是方案 2 的固有代价。
- **未验证的上限**：只测到 2,000 条。更大规模（10 万条量级）没测——
  届时可能需要把 `HISTORY_PAGE` 与「加载更早」换成真正的滚动窗口。
- **没有原型对比数据**：方案 1 在本项目条件下的实际性能与工作量**没有实测**，
  上表的对比是设计层面的推理。这是本文档最需要说明的局限。

## 五、验收门槛实测（B 方案，2026-09-24）

Task 0.2 的四条门槛此前的证据状况并不好：数据层有基线，UI 层只有「物化了多少行」
这类计数断言，**没有一条门槛被直接验证过**。这里把能自动化的补上
（`tests/ui/test_message_list_limits.py`），并把不能自动化的写明理由。

| 门槛 | 现在怎么验的 | 实测（本机） |
| --- | --- | --- |
| 流式更新不导致整页重新布局 | 给每个文档挂变化计数器，跑 10,000 个增量，断言**只有流式那一行**的文档变化；另断言行对象保持同一批实例、组件数不涨 | 10,000 增益 **2.3–4.1 s**（约 0.23–0.41 ms/个）；其余行文档变化 **0 次** |
| 组件销毁后无持续增长的 QObject | 反复「清空 + 重载」并跑事件循环（`deleteLater` 要等事件循环），断言每轮水位回到同一值；另测 10 条分支来回切 | 水位 **579 → 579 → 579 → 579**（不累积） |
| 分支切换可在目标时间内完成 | 切分支 = 清空 + 渲染目标分支（控制器的实际动作），比较 100 / 1,000 / 5,000 条的分支 | **265 / 277 / 285 ms** —— 与目标分支长度基本无关 |
| 2,000 条可接受地滚动 | **滚动流畅度本身没自动化**（理由见下），改为验证决定滚动成本的性质：组件数与历史长度无关；翻页是常数成本 | 历史 200 / 2,000 / 10,000 条 → 都是 **60 行 / 579 个组件**；点一次「加载更早」**0.4–1.0 s** |

**为什么滚动流畅度不自动化**：要测的是人眼可感的流畅度，可靠做法是测连续滚动时的
帧间隔。但测试跑在 Qt 的 offscreen 平台上，**没有真实合成器**，帧时间不代表用户所见；
把帧时间写成断言，在别的机器上只会变成随机失败。因此它留作**人工观察项**，
台账里如实标注，不假装覆盖了。

**顺带测出来的两个真实数字**（不粉饰）：

- **一次「加载更早」要 0.4–1.0 秒**：因为「加载更早」会重建整窗（60 行 markdown 重排）。
  这是方案 2 的固有代价（文档 §四 已记），点击频率低时可用，但它是当前最明显的一处卡顿。
- **10,000 个增量约 2–4 秒**：每个增量走一次 `setPlainText`（该行文档整体重排）。
  真实流式每秒几十到几百个增量，折算下来余量很大；但如果将来要支持更细的增量
  （如逐字符），这里的成本模型需要改（例如节流或增量插入 `QTextCursor`）。

**仍然缺的那一条（未变）**：两个一次性原型的对比**依旧没做**。上面这些数字说明
方案 2 在本项目的门槛上站得住，但**不能替代**方案 1 的实测对比结论——
所以台账里 Task 0.2 仍是 `△`，偏差由「四条门槛都没对账」收窄为「只有原型对比没做」。

## 六、一轮 Agent run 一张卡（2026-09-27 追加）

**问题**：此前每条模型消息各建一张 `_BubbleRow`。长任务（正文 → 工具 → 正文 → …）
因此碎成多张卡：每张卡带自己的「过程消息」标签，工具 chip 挂在产生它的那张卡上，
用户看到的不是「一个任务的进展」而是碎片。

**做法**：卡片按 **run 分组**，消息按**分段**呈现——

- **结构**：`_BubbleRow`（助手卡）内部持有若干 `_AssistantSegment`，一段对应
  一条模型消息（思考块 + Markdown 正文 + 该段触发的工具 chip）；段与段之间是
  一条细分隔线。卡级共享：底部状态行（live 期间提示「正在运行工具 X…」等）与
  动作栏（复制 / Fork，整轮收敛 `mark_final` 后统一露出）。
- **live 路径**：`begin_assistant()` 在同一轮 run（`set_busy(True)` 起止之间）
  里不再新建卡片，改为往 `_run_tail` 加一段；`end_assistant` 只定稿当前段。
  「过程消息 ↳」这类逐卡标签随之消失。
- **历史路径**：载荷从 4 元组改为 `HistoryEntry(role, content, thinking,
  message_id, run_id, tool_steps)`。`_render_window` 把 ``run_id`` 相同且相邻的
  助手条目渲染进同一张卡；工具步骤随载荷走、由视图按 ``message_id`` 归段
  （取代了此前「行号 × 消息位置」的位置 zip——合并卡片后行数不再等于消息数，
  那个映射必然失效）。``run_id`` 为 None 的旧消息退回一卡一条，无需迁移。
- **翻页不切断 run**：窗口起点落在某轮中间时回退到该轮首条
  （`_align_window_start`），保证任何一页里 run 都是完整的。

**分组依据与成本**：``Message.run_id`` 此前就已落库（messages 表有该列），
所以历史合并是纯展示层改动，旧会话自动受益；用户气泡、错误提示、重试通知、
压缩悬浮窗不在 run 组内，各自照旧。Fork 点 = run 最后一条消息（与合并前语义
一致——中间卡本就不提供动作栏）；复制 = 各段 Markdown 原文按空行连接。

**顺带修掉的一个真缺陷**：正文高度自适应回调（``documentSizeChanged →
setFixedHeight``）原先依赖外层布局在下一轮事件循环里自然长高。正文套进分段
容器后多了一级布局，外层会读到缓存的旧 ``sizeHint``，晚一轮才长高——流式期间
「贴底跟随 / 上翻阅读」因此会读到中间态的滚动范围（``test_jump_to_bottom_button``
实际暴露了它）。现在 ``_fit_browser_height`` 在设定固定高度的同时显式
``invalidate()`` 父级布局缓存，同一次布局激活就拿到新高度。
