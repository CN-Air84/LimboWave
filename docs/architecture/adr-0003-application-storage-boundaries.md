# ADR-0003：应用层拥有附件存储端口与可执行依赖边界

- 日期：2026-10-14
- 状态：本轮实现；由架构守卫与附件回归测试约束
- 范围：附件存储、行索引、导出统计、domain/application 导入规则

## 背景

配置服务和凭据服务已经使用 Protocol，但附件服务直接引用加密 BlobStore。
FileService 将参数标为 object，却在读取时用 isinstance 强制要求具体实现；替身满足 get 也无法使用。
ClipboardService 跨模块调用 FileService 的私有行偏移函数。
ExportService 的图片渲染尝试读取内容，而图片计数另用 exists 判断：损坏的文件被跳过渲染，却仍算作已导出。
原有分层测试只识别 Qt 顶层导入，不能阻止 domain 反向依赖 application，或 application 依赖 ui/web/server/基础设施；包级和相对导入也缺少方向检查。

## 决策

1. 在 `application/blob_storage.py` 定义三个按用途划分的结构化端口：
   - `BlobReader.get`：文件读取和导出；不要求写入、删除、exists。
   - `BlobStore.put/get/delete`：图片与剪贴板服务。
   - `BlobPruner.prune`：停止所有生产者之后的附件回收。
2. 组合根继续创建原来的加密实现。基础设施无需继承协议；不新增存储后端，不更改文件格式、密钥和异常语义。
3. 将原有行索引算法移动为 `domain.files.compute_line_offsets`，共享稳定行号规则。
   重建登记卡时只计算一次索引；读取仍从内容重建，兼容未持久化 offsets 的既有记录。
4. 图片渲染返回 HTML 与成功嵌入数量；导出结果直接累加该数量，删除第二套存在性计数逻辑。
   保留原本的“图片不可用时跳过、不阻断整个导出”行为；仅修正统计结果。
5. 为 domain/application 的所有 Python 文件检查导入方向：
   - domain 的项目内依赖仅允许 domain。
   - application 的项目内依赖仅允许 domain/application。
   - 两层继续禁止 Qt。
   - 备份、恢复、资料库重置、SessionController 默认内存实现、同步缓存的存量基础设施依赖列出具体模块及原因。
   - 每个例外必须仍被使用，删除依赖后必须删除豁免。新业务服务不能借用其他文件的例外。

## 权衡

- **收益**：可以不建立磁盘资料库就验证服务；静态类型检查可以验证真实组合根；读服务权限需求更小；新跨层耦合会立即导致测试失败。
- **代价**：增加一个小接口模块和维护例外清单的成本。不引入容器、工厂注册系统或通用存储框架。
- **不选具体类/运行时协议检查**：能力匹配由类型检查和行为回归验证；运行时 instanceof/isinstance 不应成为替换实现的障碍。
- **不一次性清除全部例外**：备份格式、密钥迁移和默认仓库涉及不同生命周期，不应为让依赖图好看而随本轮重写。
- **守卫的局限**：AST 覆盖普通、from、相对、包级及函数内/TYPE_CHECKING 导入；不是动态 importlib 调用或第三方传递依赖的完整证明。

## 不变项与失败模式

- 生产环境仍使用加密 BlobStore；测试的内存实现只存在于测试文件。
- 缺失 blob 的 KeyError、读存储故障的异常原样传播；FileService 未配置 blob 仓时仍明确拒绝读剪贴板。
- 回收仍要求资料库静止、生产者停止、从已提交元数据收集保留 ID；不改变提交后再回收的顺序。
- 文本行号仍从 1 开始；空文件、混合换行和末尾换行语义不变。不改变编码归一化逻辑。
- 没有数据库迁移，也没有桌面/服务端生命周期、网络协议或用户界面改动。

## 验证

新增用例先在旧实现上确认失败：3 个文件读取替换用例、2 个导出用例；方向检查准确报出 5 个附件服务的反向依赖。
修复后运行附件服务、真实加密存储既有用例、纯函数测试和全量层扫描；扩大验证结果见[项目地图](../development/project-map.md)。
