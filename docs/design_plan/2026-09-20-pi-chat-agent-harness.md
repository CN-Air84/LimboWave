# 基于 Pi Agent 的聊天与 Agent 双核心 Harness 实施计划

> **执行要求：** 实施阶段按任务顺序推进，每个阶段先完成验证再进入下一阶段。Pi 的具体 API、嵌入方式和版本兼容性在开发启动时查阅官方文档确定，本计划不预判其内部接口。

**目标：** 构建一款 Windows 优先、基于 PySide6 原生界面、面向日常聊天且具备高能力上限的桌面 Harness，在保持普通聊天软件易用性的同时，提供可控的文件读取、Agent 工具、终端执行、跨站点模型路由、上下文压缩和完整请求审计。

**总体架构：** PySide6 负责原生桌面 GUI 与应用层业务，在独立进程中运行 Pi Runtime，通过本地结构化 IPC 交换命令、流式事件和工具状态。应用自身管理会话树、逻辑模型、站点路由、提示词、上下文、权限、文件读取、加密存储和请求日志，避免将长期业务状态绑定到 Qt Widget 或 Pi 内部实现。

**首版定位：** 个人自用优先，不追求公开分发、代码签名、自动更新、遥测或第三方插件生态。首版不实现 MCP。

**建议技术栈：**

- Python 3.12+
- PySide6 / Qt 6
- qasync 或等价 Qt 异步事件循环桥接
- SQLite + FTS5
- 独立文件仓库
- SQLCipher 或应用层信封加密
- Argon2id 密码派生
- Windows Hello 用户验证与 DPAPI/系统密钥封装
- Pi Runtime 独立进程
- JSON Lines、MessagePack RPC 或等价本地结构化 IPC
- pytest、pytest-qt
- PyInstaller 或 Nuitka，用于个人可安装构建

## 一、需求基线

### 1. 产品定位

产品同时服务两类场景：

1. 像普通聊天客户端一样进行轻量、连续的日常对话。
2. 在同一会话中渐进升级为 Agent，执行文件、终端和联网任务。

默认允许模型使用内置的精确文件读取工具。除读取以外的工具能力按会话授权，并限定资源范围。普通聊天不应被工具配置、审计信息和复杂面板压垮。

### 2. 首版验收范围

首版必须具备：

- 稳定的多轮聊天与流式输出。
- 逻辑模型和跨站点端点管理。
- 会话级模型、站点和思考强度控制。
- 图片附件原图直传。
- TXT、Markdown 和剪贴板临时文档的精确范围读取。
- 消息编辑或重试后自动创建分支。
- 自动上下文压缩，且结果可查看、编辑、重试和回退。
- 消息白名单，降低或禁止压缩指定消息。
- 内置文件、目录、终端和基础联网工具。
- “内置工具模式”和“模型直接操作终端模式”两种执行方式。
- 增强 PowerShell 适配。
- 会话级持久权限和资源范围。
- 工具调用横向折叠卡片及一键隐藏。
- 停止后保留已生成内容，并支持继续对话。
- 仅连接类错误自动重试。
- 当前站点失败后，切换备用站点前要求用户确认。
- 完整原始请求与响应日志。
- 仅对会话消息进行本地搜索。
- 全量默认加密。
- 当前分支单文件 HTML 导出。
- 加密完整备份包。

### 3. 非目标

首版明确不实现：

- MCP Server 接入。
- DOCX、PDF、XLSX、PPTX 原生解析。
- 内置 OCR。
- 浏览器自动化。
- 向量或语义搜索。
- 第三方 Python 插件。
- 多人协作、账号同步或云同步。
- 移动端、macOS、Linux 客户端。
- 自动更新、公开应用商店分发、遥测。
- 普通 USB 外设绑定、硬件认证器。
- 自动静默跨站点重发。
- 非标准正文标签中的 reasoning 自动解析。

未明确的次要交互参照 Codex Desktop，但不得覆盖本计划已经确定的行为。

```text

            │                       │
┌───────────▼───────────┐  ┌────────▼────────────────────┐
│ Pi Runtime Adapter    │  │ Built-in Tool Runtime       │

┌─────────────────────────────────────────────────────────┐

│ SQLite │ FTS5 │ 文件仓库 │ 请求日志 │ 备份与导出       │
└─────────────────────────────────────────────────────────┘
```

### 1. 架构原则

- GUI 只负责展示状态和发出命令，不持有权威业务状态。
- Pi Runtime 不直接管理应用数据库、权限和长期会话结构。
- 所有模型请求先生成不可变的“拟发送请求快照”，再交给运行时。
- 工具调用必须经过应用工具网关，不能绕过权限层。
- 站点端点与逻辑模型分离。
- 加密数据库是权威数据源，文件仓库只保存由数据库引用的对象。
- 任何自动压缩、站点回退或工具调用都必须可追溯。

## 三、界面与交互设计

### 1. 主窗口

采用现代聊天型轻量双栏布局：

- 左栏：会话列表、创建会话、搜索、设置入口。
- 中央：当前分支消息流和输入区。
- 输入区右侧：约占可用宽度 15% 的会话工具栏，默认展开，可收起。

输入区本身只保留：

- 添加附件。
- 发送。
- 停止。

右侧工具栏常驻：

- 当前逻辑模型。
- 实际调用站点。
- 思考强度。
- 添加附件。
- 当前文件。
- 上下文占用情况。
- 压缩按钮。

压缩按钮采用“长按后弹出确认”的方式，减少误触。

二级抽屉包含：

- 持久权限及资源范围。
- 温度。
- 最终请求参数。
- 提示词层级与最终合成结果。
- 路由候选和回退顺序。
- 请求日志。

### 2. 消息流

每条消息以结构化消息卡呈现，但对用户保持普通聊天外观。

附件、文件片段和工具结果采用引用卡片嵌入消息，不支持首版中的任意内容块重排。

工具过程：

- 工具步骤在助手消息中横向排列。
- 默认折叠，只显示名称、状态和简短摘要。
- 展开后显示参数、返回范围、结果、耗时、审批记录和错误。
- 提供全局一键隐藏工具步骤。
- 隐藏只影响展示，不删除审计数据。

### 3. 长消息性能

不得把全部会话拼成单个 QTextBrowser。

优先验证两条实现路线：

1. QListView + 自定义 QAbstractListModel + Delegate。
2. 虚拟化消息容器，每条可见消息使用独立组件。

在技术预研阶段以以下场景进行原型比较：

- 2,000 条短消息。
- 200 条包含长 Markdown 的消息。
- 连续流式追加 10,000 个文本增量。
- 50 张图片。
- 100 个工具步骤卡片。
- 多分支切换。

选择依据是滚动流畅度、增量布局成本、组件复用难度和可访问性，而不是实现速度。

## 四、逻辑模型与站点体系

### 1. 核心概念

**逻辑模型**是用户认知中的统一模型，例如某个具体版本的 Claude、GPT 或 DeepSeek。

**站点端点**表示某个站点上的实际调用入口，包括：

- 站点 ID。
- 协议类型。
- Base URL。
- 认证引用。
- 实际模型 ID。
- 参数白名单。
- 请求头规则。
- 超时与连接重试策略。
- 能力声明。
- 优先级。

界面和调用入口按“逻辑模型 → 站点”组织，而不是传统的“站点 → 模型”。

### 2. 归一规则

- 用户可以手动把多个站点端点绑定到一个逻辑模型。
- 自动建议匹配时忽略模型 ID 大小写。
- 自动建议匹配时忽略末尾 `-free`。
- 自动规则只用于建议或初始归类，用户绑定结果具有最高优先级。
- 不根据模糊相似度擅自合并模型。

### 3. 路由规则

- 每个逻辑模型有默认站点。
- 用户可在会话级选择实际站点。
- 可以为逻辑模型配置有序备用端点。
- 当前站点连接重试耗尽后，暂停当前轮。
- 展示备用端点、失败原因和参数差异。
- 用户确认后才向备用站点重新发送。
- 不对鉴权失败、参数错误、限流或服务端业务错误自动跨站点重发。

### 4. 站点兼容预设

站点预设管理：

- 协议类型。
- 地址与认证。
- 默认请求头。
- 模型 ID 映射。
- 参数白名单与删除规则。
- 流式响应格式。
- 标准 reasoning 字段解析。
- 图片输入格式。
- 工具调用格式。
- 错误分类。

模型级覆盖管理：

- 上下文窗口。
- 输出上限。
- 思考强度取值。
- 视觉能力。
- 工具能力。
- 模型特有参数。
- 站点实际模型 ID。

任何额外参数必须有明确来源，不允许运行时私自注入来源不明的字段。

## 五、提示词体系

采用四层组合：

1. 全局基础提示词。
2. 场景预设。
3. 逻辑模型适配提示词。
4. 会话指令。

此外，工具运行时可以注入短期规则，例如：

- TXT/MD 读取必须指定起止行。
- 单次不得超过当前行数上限。
- 长内容优先调用读取工具，不要求用户整段粘贴。
- PowerShell 命令规范。
- 上下文压缩时白名单消息不得压缩。

要求：

- 发送前可查看最终拼装结果。
- 每一层可单独启停。
- 会话可覆盖上层默认值。
- 工具规则与用户角色提示词分开存储。
- 提示词版本写入请求快照，确保历史请求可复现。

## 六、会话、消息与分支

### 1. 会话模型

核心实体包括：

- Conversation
- Branch
- Message
- MessageRevision
- Attachment
- FileReadRecord
- ToolInvocation
- ContextCompression
- RequestSnapshot
- PermissionGrant

### 2. 自动分支

以下操作自动创建新分支：

- 编辑历史用户消息。
- 从旧消息重新生成。
- 替换旧消息内容后继续。
- 从上下文压缩前状态回退并继续。

旧分支永不原地改写。

工具调用、文件读取记录、请求日志和压缩记录都归属于具体分支及消息节点。

### 3. 停止和续写

按下停止后：

- 立即取消当前模型请求。
- 尽力终止尚未启动的后续工具步骤。
- 保留已生成文本。
- 保留已完成工具步骤。
- 将助手消息标记为 `cancelled` 或 `partial`。
- 用户可以直接追问、请求继续，或从该节点创建分支。

不得因取消而静默删除部分输出。

## 七、上下文管理与压缩

### 1. 自动触发

- 按逻辑模型上下文窗口计算占用。
- 支持全局配置触发阈值。
- 达到阈值后生成压缩预览。
- 用户可编辑、重试、接受或取消。
- 压缩失败时保持原始上下文不变。

建议初始默认值：

- 70%：显示即将需要压缩的提示。
- 80%：生成压缩预览。
- 90%：阻止可能超限的发送，除非用户调整上下文。

具体默认值可在可用性测试后调整。

### 2. 压缩专用模型

用户可指定独立的压缩逻辑模型和站点。

压缩请求应包含：

- 待压缩消息。
- 必须保留的事实类型。
- 当前会话目标。
- 文件读取引用。
- 已完成与未完成任务。
- 用户标记的白名单消息。
- 禁止编造缺失信息的规则。

### 3. 白名单消息

用户可以标记重要消息。

压缩时：

- 白名单消息默认保留原文。
- 通过明确提示词要求压缩模型不压缩该消息。
- 若上下文确实无法容纳，必须提示用户处理，不能静默破坏白名单语义。

### 4. 压缩结果

采用“直接替换旧消息”的拟发送上下文形式，但原始消息永久保留在数据库中。

每次压缩保存：

- 输入消息范围。
- 原始 Token 估算。
- 压缩后 Token 估算。
- 压缩模型与站点。
- 压缩提示词版本。
- 生成结果。
- 用户编辑后的结果。
- 当前启用版本。
- 创建时间和状态。

用户可查看、编辑、重试和回退任意版本。

## 八、文件与附件

### 1. 首版原生格式

支持：

- `.txt`
- `.md`
- `.jpg`
- `.jpeg`
- `.png`
- 剪贴板长文本临时文档

不支持 DOCX。

### 2. TXT 和 Markdown 精确读取

工具参数至少包括：

```json
{
  "file_id": "stable-id",
  "start_line": 1,
  "end_line": 200
}
```

规则：

- 行号从 1 开始。
- 默认单次最多读取 200 行。
- 全局可修改默认上限。
- 会话可覆盖上限。
- 超过上限时拒绝调用。
- 返回明确的申请范围、允许上限和建议分段。
- 不擅自截取前 200 行。
- 不自动拆为多次调用。
- 每次记录文件指纹、修改时间、内容哈希、申请范围和实际范围。
- 文件发生变化后，旧记录仍指向当时读取版本或明确标记版本不一致。

返回结果应包含：

```json
{
  "file_id": "stable-id",
  "path": "C:\\example\\notes.md",
  "requested_range": [1, 200],
  "actual_range": [1, 200],
  "total_lines": 864,
  "content_hash": "...",
  "text": "..."
}
```

### 3. 剪贴板临时文档

- 长剪贴板文本可保存为应用托管临时文档。
- 分配稳定 ID 和行号。
- 使用同一读取工具。
- 默认加密存储。
- 用户可重命名或删除。
- 删除前检查是否仍被会话引用。

### 4. 图片

- 视觉模型优先发送原图。
- 界面显示格式、尺寸、文件大小和估算上下文占用。
- 任何压缩或缩放都必须明确显示。
- 原始图片保留在加密文件仓库。
- 不支持视觉的模型不得静默执行 OCR。
- 可提示用户切换视觉模型或后续使用联网/外部方案。

## 九、Agent 工具体系

### 1. 两种模式

#### 内置工具模式，默认

模型调用结构化工具：

- 精确文件读取。
- 目录列表。
- 文件搜索。
- 文本搜索。
- 创建文件。
- 修改文件。
- 读取 URL。
- 网页搜索。
- 受控命令执行。

优势是参数可校验、权限边界明确、日志结构化。

#### 直接终端模式

模型通过终端完成文件、联网和系统任务。

使用场景：

- 内置工具无法覆盖的复杂命令链。
- 用户明确偏好命令行。
- 需要调用现有本地工具。

会话中必须清晰显示当前模式，避免用户误以为执行仍受内置工具的细粒度约束。

### 2. 工具网关

所有工具调用经过统一工具网关：

```text
模型工具请求
  → 参数模式校验
  → 权限与资源范围检查
  → 高影响操作检查
  → 执行
  → 输出限制与敏感信息处理
  → 审计记录
  → 结构化结果返回
```

### 3. 内置联网工具

首版提供：

- 网页搜索。
- URL 内容读取。

边界：

- 不做浏览器自动化。
- 不代替用户登录网站。
- 不自动提交表单。
- 默认禁止访问本机环回、私有网段和云元数据地址，除非用户显式授权。
- 记录最终 URL、重定向、状态码、内容类型和截断情况。
- 网页文本设定大小上限，超过时要求模型分段或缩小目标。

## 十、增强 PowerShell 适配

### 1. 执行环境

终端模式默认使用 PowerShell 7；若不可用，可回退 Windows PowerShell，但必须在界面明确显示。

每次会话向模型提供环境信息：

- Shell 名称和版本。
- Windows 版本。
- 当前工作目录。
- 默认编码。
- 路径语法。
- 可用命令和限制。
- 禁止假设 Bash 语法。

### 2. 编码

执行层统一：

```powershell
[Console\]::InputEncoding = [System.Text.UTF8Encoding\]::new($false)
[Console\]::OutputEncoding = [System.Text.UTF8Encoding\]::new($false)
$OutputEncoding = [System.Text.UTF8Encoding\]::new($false)
```

同时处理：

- 子进程输出编码探测。
- CRLF 与 LF 归一化。
- BOM。
- 中文路径和中文输出。
- 非 UTF-8 遗留命令。

### 3. 命令包装

不要直接把任意长命令拼入单行 `powershell -Command`。

优先流程：

1. 创建受控临时 `.ps1`。
2. 使用 UTF-8 无 BOM 写入。
3. 设置明确工作目录。
4. 注入严格错误处理。
5. 执行脚本文件。
6. 分别捕获 stdout、stderr、退出码和超时。
7. 执行后清理临时脚本。

### 4. 常见误用检测

执行前静态检测典型 Bash 语法：

- `export FOO=bar`
- `VAR=value command`
- `&&` 兼容性问题
- `source file`
- `rm -rf`
- `cp`、`mv` 参数差异
- `/dev/null`
- Bash heredoc
- 单引号与变量展开误用

检测到疑似误用时：

- 不自动把命令改成另一条并立即执行。
- 返回结构化诊断。
- 给模型一次生成 PowerShell 修正版的机会。
- 修正版仍正常经过权限检查。

### 5. 退出码与错误

返回：

```json
{
  "shell": "pwsh",
  "command_id": "...",
  "working_directory": "...",
  "exit_code": 1,
  "timed_out": false,
  "stdout": "...",
  "stderr": "...",
  "powershell_errors": []
}
```

不得仅凭 stderr 非空判定命令失败，也不得仅凭退出码 0 忽略 PowerShell 非终止错误。

## 十一、权限模型

### 1. 会话级持久授权

授权按会话永久保留，重新打开会话时自动恢复。

界面只在状态栏显示权限状态，不额外阻断用户。

用户可随时查看、撤销或缩小授权。

### 2. 能力与资源范围

授权记录同时包含能力和边界：

- 文件读取：允许的文件或目录。
- 文件写入：允许的目录。
- 终端：工作目录、命令类别或完全允许。
- 联网：允许的域名或全部公网。
- 模式：内置工具或直接终端。

以下行为即使已有会话授权，也应额外确认：

- 删除大量文件。
- 覆盖关键文件。
- 读取凭据或密钥目录。
- 向外部服务发布内容。
- 明显超出既有资源范围。
- 跨站点重新提交当前轮请求。

### 3. 审计

每次权限决策保存：

- 会话。
- 工具。
- 申请参数。
- 匹配规则。
- 结果。
- 是否用户确认。
- 时间。
- 实际执行范围。

## 十二、本地存储与加密

### 1. 存储结构

使用 SQLite 保存：

- 会话和分支。
- 消息和修订。
- 逻辑模型和站点。
- 提示词。
- 权限。
- 压缩版本。
- 工具元数据。
- 请求日志索引。
- 搜索索引。

使用文件仓库保存：

- 图片。
- 剪贴板临时文档。
- 大型工具结果。
- 请求与响应原始载荷。
- 导出缓存。
- 备份临时对象。

### 2. 加密策略

全量默认加密：

- 数据库加密。
- 文件仓库逐对象加密。
- API 密钥加密。
- 原始请求和响应日志加密。
- 临时文档加密。
- 临时明文文件尽量只存在于受控短生命周期目录。

采用信封加密：

- 随机生成资料库主密钥。
- 主密码通过 Argon2id 派生密钥加密资料库主密钥。
- Windows Hello 恢复封装保存另一份受系统保护的资料库密钥包装。
- 修改主密码只重新封装主密钥，不重写全部数据。

### 3. 解锁和恢复

- 应用每次启动要求主密码。
- 应用运行期间不因闲置、最小化或系统锁屏自动再次要求密码。
- 初始化时默认启用 Windows Hello 恢复。
- 忘记密码时调用 Windows Hello。
- Windows Hello 验证通过后允许重置主密码。
- 应用不读取或保存 Windows PIN。
- 用户可关闭 Windows Hello 恢复，但需明确提示风险。

## 十三、请求日志与错误恢复

### 1. 完整请求快照

每轮请求创建不可变快照，包含：

- 逻辑模型。
- 实际端点。
- 协议。
- 最终 URL。
- 请求头名称及脱敏后的值。
- 最终参数。
- 最终提示词。
- 实际发送消息。
- 文件片段与附件引用。
- 上下文压缩版本。
- 工具定义。
- 时间、耗时和状态。
- 原始响应。
- 流式事件。
- 解析后的最终消息。
- 重试和回退记录。

密钥、Authorization 和已知敏感字段在 UI 中脱敏，但加密原始日志是否保存完整凭据应默认禁止。

### 2. Reasoning 展示

- 只读取协议明确提供的标准 reasoning/thinking 字段或标准内容块。
- 不解析正文中的 `<think>` 等非标准标签。
- 标准 reasoning 默认折叠。
- 原始响应仍保存在加密日志中。

### 3. 自动重试

只自动重试连接类错误：

- DNS 临时失败。
- 建连失败。
- 连接重置。
- 流在未产生有效内容前异常中断。
- 明确的网络超时。

不自动重试：

- 鉴权失败。
- 参数错误。
- 限流。
- 业务错误。
- 已产生副作用的工具调用。
- 已输出大量内容后的流中断。

采用有限次数退避，次数和等待时间由站点预设配置，并在消息内显示。

## 十四、搜索、导出与备份

### 1. 历史搜索

首版只搜索：

- 会话标题。
- 用户消息。
- 助手最终回答。

不搜索：

- 文件片段。
- 工具结果。
- 请求日志。
- reasoning。
- 压缩内部提示词。

使用 SQLite FTS5，并支持基本时间筛选。

### 2. HTML 导出

- 每次只导出当前分支。
- 生成单文件 HTML。
- 图片以内嵌资源方式保存。
- 工具步骤可折叠。
- 保留模型和站点信息。
- 默认不包含完整请求头、密钥和原始请求日志。
- 导出前显示隐私提示。
- 导出文件不是加密文件。

### 3. 完整备份

生成加密备份包，包含：

- 数据库。
- 文件仓库。
- 站点和逻辑模型配置。
- 提示词。
- 权限。
- 请求日志。
- 版本清单和完整性哈希。

备份使用独立备份密码，不依赖当前 Windows Hello 环境，以便迁移到新设备。

恢复前：

- 验证包完整性。
- 显示版本和内容统计。
- 检查迁移兼容性。
- 先恢复到临时目录。
- 成功校验后再切换资料库。

## 十七、首版验收标准

### 聊天

- 连续聊天和流式输出稳定。
- 停止后部分内容仍保留。
- 编辑历史消息会创建分支。
- 标准 reasoning 正确折叠。
- 长会话滚动无明显持续卡顿。

### 模型与站点

- 同一逻辑模型可绑定多个站点。
- 模型 ID 忽略大小写和 `-free` 后缀后可提出正确归一建议。
- 用户可固定实际站点。
- 连接失败重试耗尽后，切换站点前必须确认。
- 请求日志能够解释每个最终参数的来源。

### 文件

- TXT/MD 必须按精确行范围读取。
- 默认单次上限 200 行。
- 超限调用被拒绝并要求模型重试。
- 每次读取的申请范围与实际范围可见。
- 图片原图可发送至视觉模型。
- DOCX 被明确标记为不支持，而不是错误解析。

### 上下文

- 达到阈值后出现压缩预览。
- 压缩可编辑、重试、接受和回退。
- 白名单消息不会被静默压缩。
- 压缩失败不破坏当前有效上下文。

### Agent

- 默认使用内置工具。
- 用户可切换直接终端模式。
- 会话权限持久保存。
- 越界请求重新确认。
- 工具步骤可展开、一键隐藏。
- PowerShell 中文输出、路径、转义、退出码和超时行为可预测。

### 数据

- 数据库、附件和请求日志默认加密。
- 启动要求主密码。
- 运行期间不自动重复锁定。
- Windows Hello 可用于重置主密码。
- 当前分支可导出单文件 HTML。
- 完整加密备份能在干净环境恢复。

## 十八、主要风险与应对

### 1. PySide6 富文本和长列表性能

**风险：** 原生 Widget 在大量复杂消息下布局成本过高。

**应对：** Phase 0 先做性能原型；采用虚拟化；流式更新做批量节流；代码块和图片延迟渲染。

### 2. Pi Runtime 集成不确定性

**风险：** 实际 API、事件模型或工具生命周期与当前抽象不同。

**应对：** 不修改总体产品边界；在 Phase 0 阅读官方文档后实现适配器；以应用自有 IPC 合同隔离变化；避免长期 Fork。

### 3. 全量加密与搜索冲突

**风险：** FTS 和对象文件加密增加实现复杂度。

**应对：** 搜索索引只存在于加密数据库；解锁后查询；锁定状态不开放搜索；备份进行完整性验证。

### 4. PowerShell 行为复杂

**风险：** 编码、非终止错误、原生命令和转义产生大量边缘问题。

**应对：** 使用脚本文件执行；建立真实 Windows 测试矩阵；结构化捕获错误；对 Bash 误用提供诊断而不是盲目转换。

### 5. 请求兼容性

**风险：** 中转站协议近似但不完全兼容官方格式。

**应对：** 站点预设和模型覆盖；严格字段白名单；完整请求快照；不注入来源不明参数。

### 6. 上下文压缩损失

**风险：** 自动摘要遗漏关键约束。

**应对：** 压缩前预览；白名单；版本化；可回退；明确显示实际发送上下文。

### 完成说明：Task 0.3 的恢复闭环（原「Phase 1C」）

- **恢复契约**：`domain/runtime_state.py` 定义了内核无关的
  `RuntimeStateSnapshot` / `RuntimeRestoreResult` / `RuntimeValidationResult`，
  以及七态恢复状态机（available → lost → restarting → restoring → validating → recovered / recovery_failed）

- **内核接口扩展**：`AgentKernel` 新增 `export_runtime_state()` / `restore_runtime_state()` /

  以及 `RUNTIME_RESTORE` 能力标志。`PiKernelAdapter` 全部实现。
- **语义指纹**：`EntryFingerprint` 按条目类型、角色与规范化内容摘要匹配。
  **不比 `parent_position` / `branch_position`**——恢复后 Pi 可能分配不同的 entry ID，
  导致父引用位置变化。内容才是语义稳定点，位置是布局细节。
  （这条是实机集成测试暴露并修复的——初版比较位置信息导致 7 条中 6 条误判不一致。）
- **RuntimeRecoveryCoordinator**：独立状态机协调器（不扩 RunCoordinator）。
  恢复期间 `can_send` 为 False（明确拒绝，不隐式排队）；优雅关闭不触发恢复；
  重复退出事件幂等；恢复成功后 `make_available()` 才开放发送，**不自动重发**。
- **`runtime_instance_id`**：每次 Pi 进程启动分配新值。适配器据此区分"旧进程的迟到事件"

- **`PiRpcProcess._expected_exit`**：区分优雅关闭（stdin EOF → 预期退出，不发事件）

### 完成说明：模型→应用执行器接线（Task 7.1 遗留补齐）

此前模型发起的命令走 Pi 内置 `powershell` 工具（单行 `-Command`），§10.3/§10.5
在那条路径上不成立——BOM 规则、`$Error` 采集、进程树杀、独立元数据文件全都用不上。
这次把模型侧接回应用自己的执行器。

**接线方案：应用侧 IPC 通道 + 极薄扩展代理**

- **通道**（`infrastructure/tools/ipc_server.py`）：环回 TCP + JSONL 一请求一响应，
  端口由系统分配（不写死、不落盘猜测）。`ToolIpcServer` 收到请求后交给
  `dispatch` 回调，回调正是 `ToolGateway.invoke` 那条既有管线——
  参数校验 → 权限/范围 → 高影响判定 → 执行 → 输出限长 → 审计 → 结构化结果。
  **模型永远碰不到网关之外的东西**：扩展只是把参数原样递过来。
- **扩展侧代理**（`policy_enforcement.ts`）：`pi.registerTool` 注册 8 个应用工具
  （`read_file`/`write_file`/`edit_file`/`list_dir`/`fetch_url`/`web_search`/
  `run_command`/`describe_shell`），每个用 Typebox 声明参数模式，
  实现是 `callAppTool()`——一次调用一条 Node TCP 连接，120 秒超时。
  扩展里**没有任何业务逻辑**：不判权限、不改参数、不解释结果。
- **`defaultTools` 显式排除 Pi 内置工具**（`environment_builder.APP_TOOLS`）：
  `read`/`write`/`edit`/`bash`/`powershell` 不在清单里，因此文件与命令访问
  **必须**走应用网关，不存在「绕过网关的侧路」。
  这是一处安全设计而非配置偏好——Pi 内置工具直接读写文件系统，会跳过权限与审计。
- **启动顺序**：IPC 服务器必须在**内核之前**启动，否则凭据赶不上进程创建。
  `_wire` 因此重排，并用一个 `holder` 字典承载「后创建的协调器」给先创建的服务器引用。
  `main()` 在内核关闭**之后**停止通道。

**认证令牌走环境变量——这是防串音，不是安全边界**

令牌由 `ToolIpcSession.to_env_value()` 编码成 `LIMBOWAVE_TOOL_IPC` 注入子进程环境。
如实说明它的强度：**同用户进程可以读彼此的 environ**，所以它挡不住同用户攻击者。
它挡的是**误连**——本机上别的程序（另一个 LimboWave 实例、随手写的脚本）
连到环回端口时不会因为「端口猜对了」就获得执行能力。
这与 ADR-0002 的威胁模型一致（同一用户可写的文件视为同一本地信任边界），
因此不宣称它提供了它没有的东西。校验用 `secrets.compare_digest`，不短路比较。

**两处把「声称」变成「事实」的修正**（都是真 bug，写在这里因为值得记）：

1. **会话 id 曾回退到客户端提供的值**：`ipc_server.py` 的文档说会话 id 由服务端
   决定，代码却写 `session.conversation_id or request.get("conversation_id")`。
   改为 `conversation_provider` 回调，会话 id **只**由服务端给出，
   env 里也不再携带——客户端无法把审计写到别的会话上。
2. **超大帧会打崩处理函数**：`readline()` 在默认 64KB 流限制处先抛 `ValueError`，
   我自己的长度检查根本没机会执行。改为 `limit=MAX_FRAME_BYTES + 4096`
   并捕获 `ValueError` 回一条「请求过大」，而不是让连接静默断掉。

**「原始响应」：拿到的是解析后的响应对象，不是线上字节。**
核对过 Pi 的 `types.d.ts`：`after_provider_response` 的载荷只有 `status` 与 `headers`
（源码级事实，不是猜的），扩展**结构上就看不到 HTTP 正文**。所以落库的是
`message_end` 上的完整助手消息——`content` 块（含 toolCall）、`usage`、
`stopReason`、`errorMessage`——它们才是排错时真正要看的东西，
且都来自协议标准字段（与 §十三.2「不解析非标准标签」同源）。
界面上第一行就是明示，不假装存了原文。

**「流式事件」：存形状，不存增量文本。**
`domain/stream_tape.py` 记的是**事件序列 + 时间偏移 + 字符数**：
`http → start → thinking… → text… → tool.start/tool.end → end`。
增量文本刻意不存——最终消息里已有全文，再存一遍是双倍占用，
而排错要看的是「先思考还是先出字」「在哪一秒卡住」（相邻事件偏移差就是停顿位置）。
三条如实的上限与兜底：

- **未知事件类型不丢也不整存**：留一条截断预览（Pi 的事件类型会随版本增加，
  静默忽略会让「流里有东西但界面上没有」变成谜）。
- **超上限只截事件、计数仍完整**（`dropped` 单独记）——否则「流了多少字」就成了谎话。
- **重试标记落在失败那次的磁带上**（第几次尝试、错误类别、退避毫秒），
  正是 §十三.3 的退避时长在日志里的可核对面。

**归集锚点是「第几次 provider 请求」，不是助手消息序号。**
一次 run 里工具往返与重试都会新增请求；只有请求序号能把「这段流是谁吐的」说清楚。
`tool.end` 之后的新请求另起一条磁带，失败尝试的磁带留在原地不被覆盖。

**顺带修掉一个真缺口：脱敏只按字段名匹配，挡不住模型回显。**
`redact_body` 原先只看键名（`api_key`、`token`…），于是
「你的 key 是 sk-…」这类**正文里的凭据**会原样进日志——而上游错误消息也常把
带 key 的 URL 吐回来。§十三.1 明确要求「加密原始日志保存完整凭据应默认禁止」，
所以给 `redact_body` 补了**文本模式兜底**：任何字符串都再过一遍 `redact_text`。
代价是正文里形似密钥的片段（哪怕正是在讨论密钥）也会被抹掉——
有意取舍：日志宁可少一段可读文本，也不能留下可用凭据。幂等性仍有测试盯住。

**存储**：迁移 v6 给 `transport_snapshots` 加 `response_body_enc` / `stream_tape_enc`
两列，与 `body_enc`/`headers_enc` 同样走字段级加密。响应正文超 20 万字符时
只截断正文块并写 `_truncated` + `_original_chars`，元数据（usage/stopReason）不截。

**验证**：13 项新单测 + 1 项真实内核端到端。

- 真实内核那项最有力：起真 Pi + mock provider 的真实 HTTP 流，
  断言磁带形状（`http` 打头、末尾是 `end`、`text_chars > 0`、无截断）
  与响应对象（`stopReason=stop`、`usage` 非空、含正文块）— 不是假内核喂出来的。
- 另有：磁带聚合与截断、未知事件预览、两次请求各带各的磁带、重试归属、
  工具事件落位、响应体脱敏（模型回显的 key 被抹）、超长截断标记、
  SQLite 往返（库里查不到明文）、v5→v6 迁移列与默认值、
  对话框两个新页签渲染。

**未验证项**：没有真实站点凭据，所以「真实模型的流式响应」是按 mock 的流验证的；
真实站点若用非标准字段名传 usage（例如把用量塞进正文），这里不会强行解析——
那正是 §十三.2 的原则，宁可少显示也不解析非标准位置。

### 完成说明：「未响应」修复（悬浮窗化的启动路径）

**症状**：程序启动后窗口「未响应」，无报错退出。
**根因**：悬浮窗化时把启动解锁的密码框也换成了内建面板，却用
**asyncio 局部事件循环**等回调——而启动那一刻主 Qt 循环还没在跑，
asyncio 循环不处理 Qt 事件，面板永远收不到绘制与输入：窗口假死。
第二个连带 bug：``ask_prompt`` 的提交顺序是「先关面板、后回调」，
取消兜底挂在 ``closed`` 上，把刚提交的值覆盖成 None。

**修法**：启动同步路径改用**嵌套 Qt 事件循环**等回调（模态对话框的本质
就是这件事，只是显式做出来）：``_run_panel_until_closed`` +
``_ask_password`` / ``_ask_startup_confirm`` / ``_show_startup_alert``
三个同步助手；``ask_prompt._submit`` 改为「先回调、后关面板」。
顺带把设置页（保存报错/密钥输入/恢复开关）与权限页（缩小范围输入）
残留的原生 QMessageBox/QInputDialog 也换成了悬浮窗回调式。

**验证**：新增 5 项回归测试，直接在「无主循环」的语境里调真实
``_ask_password``/``_ask_startup_confirm``/``_show_startup_alert``——
用 ``QTimer.singleShot`` 把「输入+点确定/取消/关闭」排进嵌套循环里执行，
能跑通就证明面板在嵌套循环里真的可交互。另：测试桩从
``settings_dialog.QMessageBox`` 换成 ``floating.ask_alert``。

### 完成说明：Task 0.2 的验收门槛实测（B 方案）

用户拍板走 **B 方案**：不补两个原型的 A/B 对比，但把四条验收门槛**真正测掉**，
把偏差从「四条门槛都没对账」收窄为「只有原型对比没做」。

**此前的证据状况（问题所在）**：数据层有基线（读 2,000 条 36 ms 等），
UI 层只有「物化了多少行」这类计数断言——**四条门槛一条都没被直接验证过**。

**现在每条门槛的验法与实测**（`tests/ui/test_message_list_limits.py`）：

1. **流式更新不导致整页重新布局** —— 给每个文档挂变化计数器，跑 10,000 个增量，
   断言**只有流式那一行**的文档变化（其余行 0 次）；另断言行对象是**同一批实例**
   （身份相同 → 没重建）。实测 10,000 个增量 2.3–4.1 s。
2. **组件销毁后无持续增长的 QObject** —— 反复「清空 + 重载」并**跑事件循环**
   （`deleteLater` 要等事件循环，不 pump 就会数到待销毁的残留），
   断言每轮水位回到同一值：579 → 579 → 579 → 579。另测 10 条分支来回切不涨。
3. **分支切换在目标时间内完成** —— 计划书没给「目标时间」的数字，这里自定宽上限
   并**比较不同长度的目标分支**：切到 100 / 1,000 / 5,000 条分别是
   265 / 277 / 285 ms，即成本与分支长度基本无关（真正要保证的性质）。
4. **2,000 条可接受地滚动** —— **滚动流畅度本身没有自动化**，理由写在测试里：
   测试跑在 Qt offscreen 平台，**没有真实合成器**，帧时间不代表用户所见，
   写成断言只会在别的机器上变成随机失败。改为验证决定滚动成本的性质：
   历史 200 / 2,000 / 10,000 条都只物化 **60 行 / 579 个组件**（与历史长度无关），
   翻页是常数成本，流式不重建其余行。滚动流畅度留作**人工观察项**，不假装覆盖。

**顺带测出的两个真实数字（不粉饰，已写进
[`docs/architecture/message-list-approach.md`](../architecture/message-list-approach.md)）**：

- **一次「加载更早」0.4–1.0 s**：因为它是重建整窗（60 行 markdown 重排）。
  这是方案 2 的固有代价（文档 §四已记），点击频率低时可用，但目前最明显的一处卡顿。
- **10,000 个增量 2–4 s**：每个增量走一次 `setPlainText`（该行文档整体重排）。
  真实流式每秒几十到几百个增量，余量很大；若要支持逐字符级增量，
  成本模型需要改（节流或改用 `QTextCursor` 增量插入）。

**过程中踩的两个测法坑**（都不是产品缺陷，是测量方法错了）：

- 拿 `id(browser)` 当计数器键：`findChildren` 每次返回新的 Python 包装对象，
  `id()` 会变，于是数出一个**假 0**。
- 把计数器 dict 存进 `QObject.setProperty`：会转成 `QVariantMap`，
  `property()` 读回来是**快照副本**，闭包改的是原对象——读数永远是 0。
  计数器因此改为放在模块级注册表，组件上只打整数标记号。

### 完成说明：Task 1.3 的 Hello 闸门（PowerShell 路径）

Task 1.3 此前是 △，理由是「Hello 需要 WinRT 绑定（`winrt`/`winsdk`），本项目不引入该依赖」。
用户把验收口径定为「**PIN 能通就行**」后重做了这件事，结论是：**这个降级本来不必要**。

**做法：不改依赖，改用系统自带的 Windows PowerShell 5.1。**
它能原生投影 WinRT 类型，于是可以直接调
`Windows.Security.Credentials.UI.UserConsentVerifier` ——
PIN 与生物识别由系统按本机配置决定用哪个，**两者都算通过**。
「不加依赖」与「真有 Hello 闸门」因此可以同时成立。
脚本按**随包文件**分发（`infrastructure/crypto/hello_check.ps1`，与
`policy_enforcement.ts` 同一个模式），wheel 里已验证包含。

**踩到的三个坑（都靠实机试出来，不是读文档猜的）**：

1. **WinRT 的 `IAsyncOperation` 在 PowerShell 里是裸 COM 对象**，
   `$op.Status` 读出来是 null，轮询那条路走不通，必须用
   `System.Runtime.WindowsRuntime` 的 `AsTask` 包装。
2. **`AsTask.MakeGenericMethod` 需要结果枚举的 `Type`**，而
   `[枚举名, 命名空间, ContentType=WindowsRuntime]` 这种写法对枚举**不生效**
   （对类是好的）。第一次还把枚举名记错了（`UserConsentVerification…` vs 真名
   `UserConsentVerifierAvailability`）。最终改为**从方法签名的返回类型反射取**——
   不写死名字，以后 Pi/Windows 改名也不会崩。
3. **`Assembly.Load("Windows.Security, ContentType=WindowsRuntime")` 不可用**
   （HRESULT 0x80131515），所以类型字面量只能留在原地，但脚本独立成文件后
   就不受 Python 行长限制的纠缠了。

**中文理由文本怎么传**：走**环境变量** `LIMBOWAVE_HELLO_REASON`，不写进脚本。
脚本保持**纯 ASCII**——Phase 7 实测过 PS 5.1 会把无 BOM 的非 ASCII 脚本按系统
ANSI 解析，中文直接变语法错误。环境变量是 Unicode 原生的，绕开了这一关。
有测试专门盯这条（断言理由不进脚本文件、只走 env）。

**结果只有枚举名，没有认证内容**：脚本只打印
`LIMBOWAVE_HELLO_RESULT <枚举名>` 或 `LIMBOWAVE_HELLO_ERROR <原因>`，
PIN/指纹从未离开系统组件。「日志不记录 PIN」仍是**结构性成立**的。
解析出 `HelloOutcome`（结果与错误互斥），只有 `Verified` 算通过，
**取消、超时、重试耗尽一律 fail closed**。

**实测证据（本机）**：

- 可用性探测（check 模式，**不弹任何窗**）：`Available` —— 这台机器的 Hello 是配好的。
- `verify` 模式用 3 秒短超时试跑：返回 `timeout`，即
  **类型加载 → AsTask 包装 → 泛型反射 → 真的发起了系统验证**这一整条链路都通了，
  只是没有人去输入。这条证据比「脚本能跑」强得多。
- 闸门自洽：`hello_gate()` 现在返回 `windows-hello`，`describe_protection()`
  写明「PIN 或生物识别…PIN 即可通过」。

**未验证项（如实记录）**：**真的输入一次 PIN 走完重置流程，我没有做**——
那需要人在系统对话框上打字，自动化不了。我能证明的是「验证被真正发起」，
不能证明「输入正确 PIN 后返回 Verified」（那是系统组件的行为，不由本项目代码决定）。
这条留给用户手工确认一次。

- 新增 26 项测试：解析（结果/错误/最后一条优先/空输出）、契约（纯 ASCII、无 BOM、
  只输出两种前缀、不读凭据 cmdlet、只读三个约定环境变量、运行参数、
  理由走 env）、闸门行为（只认 Verified、超时不弹窗、不可用时不发请求）、
  探测与缓存（只探一次、清缓存重探、四种非 Available 枚举）、自适应选择
  （PowerShell 可用就用、WinRT 优先、都不通退回账户级），
  以及 2 项**真实可用性探测**（无 UI，不断言 Available 而断言拿到了系统枚举值）。
- 顺带修了两处把「没有 pip 的 WinRT 绑定」等同于「降级」的旧测试——
  判定依据改为闸门自己，否则 PowerShell 路径可用时它们会误判。

### 完成说明：自动重试 / 回退确认 / 压缩自动触发 / 键盘导航（§八.3、§四.3、§七.1、§八.1）

**§八.3 自动重试**：`domain/retry.py` 是纯规则，**核心价值是钉住「不重试什么」**
（重试错了会重复副作用或丢用户已看到的内容）：

- 可重试：连接类（DNS/建连/连接重置/未产内容的流中断）+ 明确网络超时；
- **不可重试**：鉴权、参数、限流、业务错误，以及两类**重试有代价**的情形——
  **已产生副作用的工具调用**（重试会真的再做一遍）与**已输出内容后的流中断**
  （重试等于丢弃用户已读的东西）。
- 判定顺序固定：副作用 → 流中断分类 → HTTP 状态码 → 文本特征 → 业务错误；
  认不出来一律**不可重试**（宁可少重试，不可乱重试）。
- 站点预设新增 `EndpointConfig.retry`（次数/退避/上限/倍数）与 `timeout_seconds`——
  重试次数**不再全局写死**。
- 协调器在同一 run 内重发（不新建 run），并**保留失败尝试的请求/响应**，
  传输快照各带 `attempt` 号——那正是 §十三.1 要的「重试记录」。
- 重试**在消息流里显示**（虚线框提示条），不偷偷重发。

**§四.3 回退前确认**：连接类失败重试耗尽后，列出**备用站点候选**并询问

- Runtime 进程退出与错误语义。

核验结果只用于完善 `PiRuntimeAdapter`，不重新讨论已经确定的产品需求，除非官方核心存在无法绕开的硬限制。

### 核验已完成（2026-09-20）

完整报告：[`docs/architecture/pi-runtime-contract.md`](../architecture/pi-runtime-contract.md)。
核验基于 npm 发布包 `@earendil-works/pi-coding-agent@0.86.0` 的随包 `.d.ts`、实现源码与 32 份官方文档，属源码级事实。

八项核验结论：

| 核验项 | 结论 |
| --- | --- |
| 许可证与版本固定 | MIT；`node >= 22.19.0`（本机已满足）；`0.x` 无破坏性变更政策 |
| 推荐程序化入口 | `pi --mode rpc`，stdin/stdout 双向 JSONL；**无 Python SDK**，官方即推荐跨语言走 RPC |
| 流式事件结构 | 完整事件集与 `text/thinking/toolcall` 三类 delta 已确认，`contentIndex` + `delta` 拼装，`message_end` 为准 |
| 工具调用生命周期 | `tool_execution_start/update/end`；扩展侧 `tool_call` 可在执行前阻断并改写参数 |
| 取消请求能力 | `{"type":"abort"}`；已生成内容以 `stopReason:"aborted"` 保留，未执行工具产出 `Operation aborted` 错误结果 |
| 模型协议与自定义端点 | `models.json` 支持任意 `baseUrl` + 四种协议 + 完整 `compat` 开关，中转站可用 |
| Windows 支持范围 | 原生支持；`bash` 工具依赖 Git Bash；`powershell` 工具 pwsh 优先、回退 5.1 |
| Runtime 退出与错误语义 | stdin EOF→0、SIGTERM→143、SIGHUP→129、**无 SIGINT 处理器**；无正式错误码表 |

**触发"无法绕开的硬限制"的四处**，需按 §21 的例外条款重新审视相应产品需求（详见合同文档 §五）：

1. **上下文权威（影响 §2.1 / §7 / §13.1）**：RPC `prompt` 只接受单条 `message: string`，无消息数组，宿主无法自主构造发送上下文。
2. **压缩能力（影响 §7）**：Pi 无白名单/固定消息、无预览编辑重试、无版本化回退、无压缩专用模型配置项。仅能通过自建扩展的 `session_before_compact` 介入。
3. **加密（影响 §12）**：Pi 会话为明文 JSONL 落盘，`auth.json` 亦为明文，无任何内置静态加密。
4. **权限（影响 §11）**：Pi 明确不含内置权限系统、**不含内置沙箱**；面试图由 `extension_ui_request/response` 通道承载，必须自建扩展。

另有一处**隐私冲突**必须处置：`enableInstallTelemetry` 默认为 `true`，会注入 provider 归属头并上报安装信息，与 §4.4「不允许运行时私自注入来源不明的字段」及 §1.3「不实现遥测」冲突，须显式关闭。

### 核验后的路线裁决

上述硬限制**不构成更换内核的理由**。已裁决采用**应用兼容内核层**：保留 Pi，把 Pi 降级为可替换的 Agent 执行引擎，由应用定义的 `AgentKernel` 接口隔离其具体协议。四处硬限制的处置方式、权威边界划分，以及受影响的计划章节清单，见
[`docs/architecture/adr-0001-agent-kernel.md`](../architecture/adr-0001-agent-kernel.md)。

**在 ADR 落地改写之前，本文 §2.1、§7、§11、§12、§13.1、§13.3 的产品要求仍然有效，但实现路径以 ADR 为准。**

Phase 0 的收敛点为六项**内核去留闸门**（`P0-GATE-01` ～ `P0-GATE-06`），见
[`docs/architecture/pi-runtime-contract.md`](../architecture/pi-runtime-contract.md) 第十一节。

## 完成定义

当以下条件同时满足时，首版完成：

- 能作为日常聊天客户端稳定使用。
- 能按逻辑模型而非站点组织调用。
- 能准确解释最终请求中每个参数。
- 能对 TXT/MD 进行精确、受限制、可审计的读取。
- 能处理长会话且压缩结果完全可控。
- 能使用内置本地与联网工具完成基础 Agent 任务。
- 能在高级终端模式下可靠使用 PowerShell。
- 能保护本地会话、附件和日志。
- 能从真实失败中恢复，而不是只覆盖正常演示路径。
- 不依赖 MCP、DOCX 解析或浏览器自动化即可达到日常主力可用状态。
