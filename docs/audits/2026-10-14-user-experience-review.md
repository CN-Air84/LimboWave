# LimboWave 用户体验巡检与第一轮优化

日期：2026-10-14

## 总体判断

项目已经具备完整的聊天、分支、模型路由、工具权限、记忆/压缩、资料库安全和远程访问能力。当前比换一套外观更值得优先解决的是：**用户不知道发生了什么、不知道为什么不能操作，以及试探一个功能就可能丢掉输入。**

本轮沿主要用户路径审阅界面、应用接线、既有测试与设计文档，并对下述问题做增量修复；不是对每个页面或全部服务端逻辑的穷尽验证。不改变原有视觉风格，不调用真实模型、不打开用户实际资料库、不重启用户正在使用的应用，也不重新生成桌面安装包。

## 用户路径概览

| 路径 | 现状与判断 |
| --- | --- |
| 首次使用与解锁 | 已有独立引导、模型清单失败后的重试/手动添加、明确选择默认模型；保留加密和解锁边界。 |
| 配置站点与模型 | 功能较完整，但“站点端点 / 实际模型 / 逻辑模型 / 绑定”对普通用户认知负担较大；未保存保护不一致。 |
| 日常聊天 | 发送、停止、附件、历史加载、队列齐备；模型可用性此前不恰当地限制了文字编辑，操作结果提示还存在完全不可见的问题。 |
| 历史与分支 | 支持跨会话草稿、后台生成与独立浏览；编辑旧消息借用输入框时需要保护原草稿。 |
| 工具权限与上下文 | 保留权限预设、压缩确认、上下文阻断等安全约束；本轮不为方便输入而放宽执行权限。 |
| 导出、备份、重置 | 已有隐私默认项、影响说明和破坏性操作确认；备份结果等反馈以前可能只记录而没有展示。 |
| 网页与移动端 | 已有配对、密码验证、回执与 IME 保护；需要统一发送入口校验，明确模型缺失状态以及草稿保留期限。 |

## 已落实的优化

### 1. 让“无响应”的操作重新有反馈

**原问题：** `ChatView.set_status()` 只更新 `_status_text`，不展示任何内容。应用层却用这个接口提示“备份完成”“当前正忙”“无法切换模型”“没有可导出的会话”等结果，用户只能猜测。

**改动：** 在输入区内增加小型可关闭提示；“就绪”“新会话”等常态不占空间。提示使用纯文本和自动换行，避免文件名被当作 HTML；可关闭但不影响草稿，不把这些提示写成聊天消息。

**涉及：** `src/limbowave/ui/chat_view.py`。

### 2. 模型不可用，不再禁止写草稿

**原问题：** 未配置模型或模型暂时不可用时，整个文字输入框被禁用，用户无法提前组织问题，也无法方便地修改已有输入。

**改动：** 将“可以写文字”和“可以发送/添加附件”分开。不可用时允许编辑文字，明确说明原因与恢复后需手动发送；发送仍然被阻止，附件粘贴与拖放也不能绕过限制。只读视图、历史切换、压缩阶段仍保持原有保护。

同时补齐输入框、发送和停止按钮的可访问名称，并在空输入框展示真正可用的快捷键。

**涉及：** `src/limbowave/ui/chat_view.py`。

### 3. 取消编辑旧消息，可以找回原文字和附件

**原问题：** 点击历史消息的编辑按钮后，原来未发送的新问题被覆盖，附件先被清空；取消编辑只会再次清空输入。

**改动：** 在替换旧消息附件之前保存编辑前快照。取消编辑恢复原文字和附件；连续编辑不同历史消息仍保留最初的草稿；会话/分支的草稿快照同时携带编辑前状态，不把其他会话的内容恢复过来。

**边界：** 本轮保障取消编辑与会话快照恢复，不改变“提交历史编辑会创建新分支”的发送流程。草稿仍只保存在当前进程内存中，不新增明文磁盘保存。

**涉及：** `src/limbowave/ui/chat_view.py`、`src/limbowave/app.py` 的 `_prepare_edit` 接线。

### 4. 网页端不能再绕过禁用的发送按钮

**原问题：** 按钮、回车和表单提交各自判断是否发送；空模型时按钮禁用但回车仍能进入提交回调。选择的模型被移除后，原生下拉框还可能显示另一个模型，造成“看到的选择”和实际状态不一致。

**改动：** 三个入口共用发送条件，包括忙碌、生成中、禁用状态、有效模型和非空正文。失效模型明确显示“当前模型已不可用”，不假装自动选中替代模型；模型列表为空时说明应该到哪里配置，并继续允许写草稿。

保留中文输入法确认文字不发送、手机回车换行；键盘快捷键提示只在精细指针设备且非生成状态展示。草稿说明明确指出刷新或断开设备会清除内容。

**涉及：** `web/src/components/Composer.tsx`、`web/src/styles/layout.css`。

## 建议的后续优先级（本轮未修改）

1. **优先：站点配置的未保存保护。** `_EndpointsTab._on_select()` / `_on_new()` 会直接覆盖表单，`SettingsPanel.resolve_pending_changes()` 目前只处理外观编辑器。建议先统一“保存 / 放弃 / 留在当前页”，而不是只加一个保存成功提示。
2. **优先：草稿生命周期。** 目前关闭桌面程序、刷新网页或断开设备会丢弃内存草稿；本轮只让网页说明更清楚。后续需要结合资料库加密、共享设备和锁定机制设计恢复策略，不能简单把敏感内容塞进浏览器本地存储。
3. **随后：破坏性确认的键盘替代。** `SlideConfirm` 以鼠标拖动为唯一确认手势。建议增加可键盘完成、仍具二次确认强度的替代路径，不直接改成容易误按的单击删除。
4. **随后：降低模型配置术语负担。** 面向普通用户先呈现“连接服务 → 选择模型 → 开始聊天”，把路由/绑定留作进阶入口；这是信息架构调整，不宜仅做几个名称替换。
5. **随后：正在其他会话生成时的远程提示。** 网页展示全局运行状态，浏览其他会话时应明确标出正在生成的会话，避免把“停止”理解为只影响眼前的对话。

## 验证结果

- 先加入复现用例：桌面新测试初跑 **4 失败 / 4 通过**，网页输入组件初跑 **6 失败 / 6 通过**，确认测试能捕获原问题。
- 修复后桌面核心定向回归：**114 通过**，覆盖聊天视图、草稿、历史加载、发送队列展示及新增的真实应用回调测试。
- 发送队列集成单独复跑：**18 通过**，覆盖排队、取消、分支目标及后台生成等交互。
- 网页单元/组件测试：**67 通过**；TypeScript 类型检查与生产构建通过。
- 浏览器流程：**2 通过**，覆盖冲突时保留草稿、历史、IME、抽屉、320/390/430 像素竖屏与横屏；新增真实触摸环境下无模型指引、草稿输入和无横向溢出检查。
- `chat_view.py` 类型检查及本轮新增桌面测试/视图代码规范检查通过。
- 已离屏渲染并目视核对浅色/深色提示、旧消息编辑和取消恢复；同时核对手机截图。未把真实用户内容用于截图。

### 没有隐藏的验证问题

扩大组合运行时并非全绿：发生过发送队列初始化错误、一个高 DPI 截图用例失败，以及思考下拉框主题用例失败。队列全部 18 项和高 DPI 用例单独复跑通过。**思考下拉框的深色背景断言及 `_PopupMaterial` 清理异常仍可复现**，在仅换回本轮修改前的 `ChatView` 后结果相同；因此不能宣称全项目测试通过，也不在本轮越界修改正在变化的主题实现。既有 `docs/development/oobe.md` 也记录过该主题用例问题。浏览器最后一轮曾遇到测试端口被占用，未终止任何其他进程，随后两项完整复跑通过。

## 变更边界

工作区在开始时已有大量未提交修改，期间其他文件也在变化。本轮只增量修改上述聊天/输入组件、其测试与本报告，没有提交、回退或覆盖其他改动。网页构建输出已刷新；正在运行的旧程序需要下次重新启动/加载后才会使用新代码。
