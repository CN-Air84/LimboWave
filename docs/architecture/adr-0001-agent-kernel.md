# ADR-0001：采用应用兼容内核层，Pi 降级为可替换的 Agent 执行引擎

- **状态**：已接受
- **日期**：2026-09-20
- **依据**：[Pi Runtime 接入合同（核验报告）](pi-runtime-contract.md)
- **影响**：设计计划 §2.1、§4、§5、§7、§9、§10、§11、§12、§13.1、§13.3

---

## 一、背景

对 Pi 的静态核验（基于 `@earendil-works/pi-coding-agent@0.86.0` 源码）确认：Pi 在 Agent 循环、流式输出、分支、取消、工具协议与中转站兼容方面**很适合**，核验没有证明它不适合。

真正的问题是：**Pi 的产品边界与我们的产品边界不完全相同**。这应当通过架构隔离解决，而不是推倒内核。

核验识别出四处「官方核心无法绕开的硬限制」：

| # | 硬限制 | 涉及章节 |
| --- | --- | --- |
| 1 | RPC `prompt` 只接受单条 `message: string`，宿主无法提交完整消息序列 | §2.1 / §7 / §13.1 |
| 2 | Pi 压缩缺预览、编辑、白名单、专用模型、版本化、回退 | §7 |
| 3 | 会话明文 JSONL 落盘，`auth.json` 亦为明文，无内置静态加密 | §12 |
| 4 | 无内置权限系统、**无内置沙箱** | §11 |

另有隐私冲突：`enableInstallTelemetry` 默认 `true`，注入 provider 归属头并上报安装信息（§1.3 / §4.4）。

---

## 二、决策

**采用路线 C：保留 Pi，增加一层由应用掌控的「兼容内核层」，把 Pi 降级为可替换的 Agent 执行引擎。**

```text
PySide6 GUI
    │
Application Core
    │
AgentKernel 接口          ← 应用定义的稳定接口
    ├── PiKernelAdapter   ← 第一个实现
    └── FutureNativeKernel
```

应用**不直接**依赖 Pi 的具体 RPC 命令。Pi 不是产品的权威内核，而是 `AgentKernel` 的第一个实现。

---

## 三、未采纳的路线

### 路线 A：让 Pi 直接充当产品内核 —— 不推荐

会让产品能力被 Pi 的内部语义反向锁死：无法提交完整消息序列；压缩达不到可预览/可编辑/可回退/白名单要求；明文会话与凭据与默认加密冲突；权限与沙箱缺失；默认重试与「只重试连接错误」冲突；默认遥测与隐私基线冲突；PowerShell 工具达不到计划中的执行与审计标准。

能快速做出 Demo，但会把后续产品能力锁死。

### 路线 B：立即自建 Agent 内核 —— 目前不推荐

自建意味着重新实现并长期维护：多协议模型适配、流式事件归一、reasoning 内容块、工具调用循环、取消与部分输出定稿、会话树与分支、中转站兼容开关、重试与错误分类、上下文管理，以及各供应商不断变化的协议细节——这些恰是 Pi 已较成熟的部分。

**仅当出现以下任一情况，才正式启动自建内核论证：**

1. `before_provider_request` 无法稳定获得或修改最终请求。
2. `--no-session` 下无法维持可用的多轮上下文，且没有可靠的会话恢复或导入机制。
3. 扩展钩子无法在所有工具执行前实施强制权限控制。
4. Pi 升级频繁破坏 RPC 合同，兼容成本接近维护自有内核。
5. 无法真正关闭遥测、上下文文件加载或内部重试。
6. Pi 的会话压缩无法被完整接管，且会在宿主不知情时改写上下文。

当前静态核验**尚未证明**这些问题存在。

## 四、权威边界

### 1. 应用拥有权威（唯一真相源）

站点与逻辑模型配置、API 密钥、提示词分层配置、会话展示树与产品级分支、消息修订记录、附件与精确文件读取记录、上下文压缩版本、白名单消息、会话级权限与资源范围、工具执行审计、请求与响应日志、搜索索引、加密、备份与导出、自动重试与站点回退决策。

### 2. Pi 拥有运行时状态

Agent 循环、当前运行分支的模型上下文、流式增量、标准 reasoning 事件、工具调用协议、abort 与部分输出定稿、Pi 原生会话树能力、模型协议与中转站兼容。

> **关键约束：Pi 的运行时状态必须能够由应用重建，不能成为唯一不可恢复真相。**

### 3. 双方共同产生，由应用归档

Pi entry ID、fork/clone 后的节点关系、最终 provider 请求、provider 原始响应、token 使用量、`stopReason`、工具调用与工具结果、压缩前后的上下文边界、Runtime 错误与退出信息。

## 五、四项硬限制的裁决

### 裁决 1：Pi 拥有运行中的模型上下文，应用拥有产品级会话镜像

不要求应用直接构造每轮完整消息数组（RPC 入口不支持）。**设计计划中「拟发送请求快照」的表述改为二分：**

#### 请求意图快照（调用 Pi 前生成）

用户本轮输入、选择的逻辑模型与实际站点、当前产品分支、提示词配置版本、附件与文件引用、权限状态、压缩版本、工具模式、用户设置的请求参数。

#### 最终传输快照（由 `before_provider_request` 提供）

最终 URL、最终请求头（敏感值脱敏）、最终请求体、Pi 真正发送的消息序列、工具定义、最终模型 ID、最终兼容参数。

> 这比原计划只保存一个「拟发送请求快照」更严谨。

**已实机钉死（2026-09-20）：属选项 ①** —— 仅禁止持久化磁盘，会话树与多轮上下文在进程内完整存在
（28/28 项检查通过，证据见合同文档 §11.3）。故本裁决的架构直接成立，无需替代入口或局部 Fork。

### 裁决 2：压缩由应用制定策略，Pi 执行时通过扩展接管

不接受 Pi 原生压缩作为产品最终行为。推荐流程：

```text
Pi 触发 session_before_compact
    → 扩展暂停默认压缩
    → 通知应用需要压缩
    → 应用选择消息范围与白名单
    → 调用压缩专用模型
    → 用户预览、编辑或重试
    → 应用返回自定义摘要
    → Pi 继续当前运行会话
```

两级策略：**自动模式**按既定规则生成摘要并继续，同时保留回退版本；**审阅模式**发送前展示压缩预览。用户已选「自动触发并可预览」，准确实现为：**自动生成，默认展示短暂的非阻塞预览入口，仅当上下文即将硬超限时才阻断发送。**

**若钩子只能同步返回、不能等待 GUI 审阅**，降级为：① 在 70%～80% 阈值由应用主动发起压缩；② 完成后把摘要准备好；③ Pi 真正触发 `compact` 时直接注入已批准摘要。这比在钩子里等 UI 更稳定。

### 裁决 3：使用 `--no-session`，禁止 Pi 持久化权威数据

方向正确，但须实机确认不破坏多轮能力。密钥与配置管理：

- API 密钥只存应用加密资料库。
- 启动 Pi 时通过一次性环境变量注入。
- `models.json` 仅引用 `$ENV_VAR`。
- **禁止写入 Pi 的 `auth.json`**。
- Pi 工作目录使用应用创建的受控临时目录，退出后清理。
- **禁止使用真实用户的默认 `~/.pi` 目录**；明确设置独立的 `PI_HOME` 或等效目录（若 Pi 支持）。
- IPC stdout 只允许 JSONL，诊断日志进 stderr 或独立日志通道。

`--no-context-files` **进入强制启动基线，不是用户可选项**。否则打开陌生项目时 `AGENTS.md` / `CLAUDE.md` 会形成未经应用提示词层管理的隐式输入。

### 裁决 4：权限完全由应用掌控，Pi 只提供拦截通道

不构成换内核理由——Pi 明确不提供权限弹窗，反而让边界更清楚。实现为强制性的 `PolicyEnforcementExtension`：

```text
Pi tool_call → 扩展拦截 → 应用
                            ├── allow
                            ├── deny
                            ├── rewrite
                            └── ask_user
                         → 扩展才允许继续执行
```

强制约束：

- 未收到应用响应时**默认拒绝**；应用断连时**默认拒绝**。
- 不允许 Pi 自带工具绕过扩展。
- 所有工具必须有稳定的工具 ID 与参数模式。
- 参数改写后必须重新记录最终参数。
- 直接终端模式**不能**复用「内置工具已授权」的假象。
- 高影响命令必须由应用二次确认。
- 工具执行结果必须回传应用归档。

**若某些内置工具无法被 `tool_call` 可靠阻断**，最稳妥的方式不是换内核，而是**启动时不注册这些工具，改注册应用提供的代理工具**。

## 六、重试归属：关闭 Pi 自动重试，应用全权控制

理由：产品要求只自动重试连接错误；必须显示次数、原因与等待时间；必须避免对已产生输出或副作用的请求重复执行；跨站点回退必须用户确认；Pi 默认的三次退避无法表达这些规则。

分层：

- **Provider 请求重试**：由应用根据 Runtime 返回的结构化错误分类决定。
- **工具重试**：默认不自动重试，除非工具明确声明幂等，且失败发生在执行前。
- **Runtime 进程重启**：可自动重启 Pi 进程，但**不得**自动重发上一轮用户请求。

**须实机确认能否完全关闭 Pi agent 重试。** 若不能，视为真正的兼容阻断项——因为应用看到的「一次调用」可能已在内部请求多次。

## 七、启动硬性断言

以下各项在启动 Pi 前必须成立。**应用应读取实际生效配置并校验；若发现遥测仍启用、上下文文件仍启用或内部重试无法关闭，应拒绝启动 Runtime，而不是仅写一条警告。**

- `enableInstallTelemetry = false`
- `--no-context-files`
- `--no-session`（语义待 P0-GATE-01 钉死）
- 禁用内部重试
- 禁用自动审批，或对所有工具前置拦截
- 使用隔离配置目录
- 不读取默认 `auth.json`
- 不读取用户全局 Pi 配置
- 不加载未声明扩展
- 不允许来源不明的 provider headers

## 八、PowerShell：两条清晰路径

不强行修补 Pi 的 PowerShell 工具以凑满计划要求。

### 默认：内置工具模式（应用自建执行器负责）

临时 `.ps1`、UTF-8 输入输出、stdout 与 stderr 分离、exit code、非终止错误、超时与取消、Bash 误用诊断、工作目录与权限边界、完整审计。

### 高级：Pi 直接终端模式（明确标记为兼容模式）

使用 Pi 原生 PowerShell 行为；UI 显示「Pi 原生终端」；**不宣称**具有应用执行器的全部编码与错误保证；仍通过权限扩展做执行前审批；保留完整命令与输出日志。

用户选择直接终端模式时提供两个子选项：① 应用增强终端（推荐）；② Pi 原生终端（兼容与调试用途）。

这样不必为一个工具的实现差异 Fork 整个 Pi。

## 九、AgentKernel 接口定义

不写薄薄的 `PiRuntimeAdapter`，而是正式定义 `AgentKernel`：

```text
AgentKernel
├── capabilities()
├── start_session()
├── restore_session()
├── send_message()
├── abort()
├── fork()
├── clone_branch()
├── get_entries()
├── inject_tool_result()
├── prepare_compaction()
├── apply_compaction()
├── subscribe_events()
└── shutdown()
```

能力协商：

```text
KernelCapabilities
├── persistent_session
├── in_memory_session
├── branching
├── abort_preserves_partial
├── final_request_hook
├── custom_compaction
├── tool_preflight_hook
├── internal_retry_disable
└── telemetry_disable
```

**应用不得假定所有能力都存在。** 启动时由 `PiKernelAdapter` 返回能力集，缺失硬要求时**直接报告不兼容**。

未来即使 Pi 出现不可接受的变化，也可实现 `PiKernelAdapterV2`、自建 `NativeKernel` 或其他 Runtime 适配器，而 GUI、数据库与绝大部分产品逻辑无需重写。
