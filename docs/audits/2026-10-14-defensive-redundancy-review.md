# 过度防御与重复工作的性能审计

日期：2026-10-14（Asia/Shanghai）

## 结论与范围

找到了五处有可复现证据的重复工作。前三处位于网页流式输出路径，应优先处理；后两处分别影响桌面动态组件和异常恢复。问题不是“检查太多”，而是为了检查反复创建校验器、物化整份状态、序列化同一对象或重新读取已验证的数据。

本轮仅审阅和复现，没有修改业务源码、没有删除安全检查、没有访问真实资料库或启动模型请求。工作区存在其他进行中的修改；以本轮复现时的当前工作树为依据，不把现有未提交修改归为本轮成果。复现相关源文件 SHA-256 另保存在 `.var/redundancy-audit-2026-10-14/source-hashes.json`。

项目主干概览：

- 桌面装配：`src/limbowave/app.py`；Qt 界面：`src/limbowave/ui/`。
- 应用业务：`src/limbowave/application/services/`，以 `RunCoordinator`、`SessionController`、`RuntimeFacade` 连接运行和展示。
- 领域与持久化：`src/limbowave/domain/`、SQLite 仓储、加密、分支路径与历史分页。
- 模型运行：`PiKernelAdapter`、RPC、运行环境构建、运行时恢复。
- 服务端与网页：`src/limbowave/server/`、`src/limbowave/web/`、`web/src/`。
- 辅助路径：日志脱敏、备份恢复、配置、工具步骤。

这是项目结构概览和关键调用链审阅，不是声称逐行验证全部文件，也不是完整端到端性能分析。

## 1. 网页逐 token 创建同一个 Zod 校验器

**优先级：高；修改风险：低。**

位置：`web/src/state/chat.ts:157`。

```ts
const { text } = z.object({ text: z.string() }).parse(event.payload);
```

正文和思考增量每次进入 `applyEvent` 都会重新构造 schema。`controller.ts` 的 40 ms 延迟只合并通知界面的时机，不会合并此前逐事件执行的 `applyEvent`，因此这项创建成本仍按事件数支付。

这里多余的是 **schema 创建**，不是校验本身。不需要把后端数据认定为可信，不需要删除 `parse`；把相同 schema 放在模块作用域复用即可。

复现：直接从当前源码内存打包两份 reducer；对照版只提升 schema，其他代码不变。每组处理 10,000 个增量、1 条消息，预热后交替运行 7 轮，中位数：

| 当前实现 | 只复用校验器 | 状态一致性 |
|---:|---:|---|
| 139.09 ms | 3.34 ms | 7 轮最终完整状态深比较一致 |

这只是 Node v24.12.0 下的合成 reducer 局部耗时，不含网络、React 或绘制，不能当作整个应用的提速倍数。

建议回归：有效增量、非法 payload、正文/思考分支均保持原行为；不删除输入校验。

## 2. SSE 每个事件两次完整快照，只取一个布尔值

**优先级：高；修改风险：低到中。**

位置：

- `src/limbowave/web/stream.py:99` 和 `:107`。
- `src/limbowave/application/services/runtime_facade.py:86-118`。
- `src/limbowave/application/services/run_coordinator.py:461-475`。

两处都执行：

```python
if not (await facade.state()).get("available", True):
```

`state()` 不只是检查有效性：还会调用 `stream_snapshot()`，遍历全部工具步骤与输出分段，创建展示字典。但 SSE 此时仅使用 `available`，其余内容马上丢弃。若事件已到达，第一次检查到第二次检查之间只有条件判断与 `break`；当前真实 `state()` 内部也没有 `await`，不会在这两次检查之间主动让出事件循环。

复现：真实 `RuntimeFacade.state` + 真实 `RunCoordinator.stream_snapshot`，注入纯内存模拟运行。消费 1,000 个事件时生成 **2,001 次完整快照**，其中 1 次为流初始化。模拟 100 个工具和 100 个分段时，共创建 **400,200 个未用于输出的工具/分段字典**。

不要误解为全文字符串深复制：当前正文、思考字符串只是引用；浪费主要是工具/分段遍历与对象分配。

建议：暴露只检查 `_valid`、`_closed`、运行可用性和 readiness 的轻量接口；每次异步等待后保留必要检查，去掉同一路径中的重复检查。真正的首次快照和同步接口仍保留完整 `state()`。

建议回归：锁库、撤销设备、断连和 readiness 变化仍及时终止流；不能为了优化删除等待后的复查。

## 3. 广播队列反复把同一事件序列化，只为计算字节数

**优先级：高；修改风险：低到中。**

位置：`src/limbowave/application/services/event_broker.py:33,58,88-89,110,121,147-149`。

同一事件经历：

1. `publish()` 序列化并计算大小；回放缓存已存 `(event, size)`。
2. 每个订阅者 `push()` 再序列化一次。
3. 每个订阅者取出事件时再序列化一次，扣减队列字节数。
4. 回放时遍历 `(event, _)`，丢掉已有大小，再交给 `push()` 重算。

在队列未溢出、所有订阅者匹配并消费的路径上，每个事件计算大小需要 `1 + 2 × 订阅者数` 次 JSON 序列化。这不包括真正发送 SSE 时的序列化。

复现：

| 事件数 | 订阅者数 | 仅计算大小的序列化次数 |
|---:|---:|---:|
| 1,000 | 0 | 1,000 |
| 1,000 | 1 | 3,000 |
| 1,000 | 4 | 9,000 |

建议：订阅队列也存 `(event_copy, size)`，沿用发布/回放时已计算的大小；出队直接扣减该值。保留字节上限、慢消费者断开和订阅者隔离。

**不要直接删除所有 `deepcopy`。** 当前测试明确允许一个消费者修改拿到的事件，并要求不污染回放；队列副本有实际作用。另有一个可选小清理：`publish()` 最后返回的 `deepcopy(event)`，当前唯一业务调用方 `RuntimeFacade._on_event()` 未使用返回值；可以在明确接口契约后避免这份无人使用的返回副本，但不能据此推导全部复制都无用。

建议回归：限额、溢出、回放、无效游标、消费者改写事件和队列关闭。

## 4. 桌面悬停效果安装：无关子对象变化也全树扫描

**优先级：中；修改风险：中。**

位置：`src/limbowave/ui/theme_effects.py:264-290`。

根对象收到每个 `ChildAdded` 都安排一个独立的零延时回调。回调遍历根下全部 QWidget，检查是否已经安装效果。即使新增的是无视觉内容的 QObject，而不是控件，也触发同样的扫描；同一批新增事件没有合并。

复现：离屏 Qt 中，300 个按钮已全部安装过滤器；向根添加 20 个普通 QObject，没有增加任何 QWidget。处理事件后仍执行 **20 次全树扫描、6,000 次现有控件访问**，不增加任何控件效果。

建议：先以 pending 标记合并同一事件循环批次的安装工作，再考虑延迟检查新增子树。不要在 `ChildAdded` 的构造中间态草率判断控件最终类型，也不要删除对象销毁检查。

这不是“每个 token 必然扫描”的问题；成本出现在根的动态子对象创建批次，影响频率比前三项低。

## 5. 异常恢复重复获取完整 entries 并计算同一组指纹

**优先级：中低；需要先统一接口契约。**

位置：

- `src/limbowave/infrastructure/pi_adapter.py:361,380-385`。
- `src/limbowave/application/services/runtime_recovery_coordinator.py:189-206`。
- 当前调用入口：`RunCoordinator._recover_runtime()`。

Pi 适配器在 `restore_runtime_state()` 内部已执行一次 `validate_runtime_state(snapshot)`，验证失败不会返回成功。恢复协调器收到成功结果后，立即再次调用同一验证接口，重新读取全部 entries、重新计算指纹。期间没有发起新模型请求。

复现：使用真实 Pi 适配器恢复逻辑、真实恢复协调器和真实指纹算法，只替换文件物化及外部 RPC。恢复 200 个模拟 entries 成功，完整 `get_entries()` 调用 **2 次**。

这是 Pi 当前实现下可消除的重复，而不是说通用 kernel 的成功返回天然等于已经验证。其他直接调用适配器恢复的路径依赖其内置校验，因此**不能只删除适配器那一层**。建议让恢复结果显式携带本次验证结果，协调器复用；未提供验证结果的实现仍走一次校验。

该项只影响异常恢复，不会直接改善日常打字/滚动。未测真实 RPC 与大历史耗时，不提供虚构毫秒收益。

## 不应误删的防御

- Qt 回调的对象存活判断：对象可在异步回调执行前销毁。
- `await` 前后的运行身份、分支、版本和权限检查：等待期间状态确实可能变化。
- 分支链循环检测及深度限制：防止损坏数据导致无限遍历。
- 备份、恢复、落盘前完整性与路径检查：边界和时间点不同，不能仅因“之前查过”删除。
- 入库脱敏、网络 DTO 白名单和权限校验：不同信任边界，不是这次性能优化应放宽的内容。
- 防止消费者改写污染回放的队列副本。

## 修复落实（2026-10-14 后续）

上述五项现已按最小变更实现。没有删除输入校验、消费者隔离、队列限额或等待后的权限/可用性复查。

### 实施内容

1. 前端 `DeltaPayloadSchema` 在模块加载时构造一次，每个增量仍执行 `parse`。
2. `RuntimeFacade.is_available()` 提供不生成输出快照的同步检查；SSE 等待后使用此接口，删除同一路径中无调度间隙的第二次检查。
3. 订阅队列保存 `(event_copy, size)`，发布和回放复用大小；resync、invalidate 和出队保持一致的字节账目。保留 `publish()` 返回副本契约，没有顺带删除所有深复制。
4. 悬停效果控制器拥有一个单次定时器，合并同批 ChildAdded；主动更新设置时取消已被覆盖的待扫描任务。定时器跟随 QObject 销毁，新增测试也发现并覆盖了原实现根对象销毁后延迟回调访问失效控件的问题。
5. `RuntimeRestoreResult` 增加末尾可选 `validation` 字段；Pi 保留内部验证并返回结果，协调器复用。旧式/未提供验证结果的 kernel 仍执行独立校验；显式失败结果仍拒绝恢复。
