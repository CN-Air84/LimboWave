# 项目性能审阅与历史恢复优化

日期：2026-10-14

## 结论与范围

本轮概览了应用服务、仓库读写、历史分页、桌面/Web 消息呈现、运行时恢复、压缩及备份路径。最终修改限定在 **3 个生产文件**：清除重复父链遍历、避免无必要的全量排序，并为普通未压缩会话保留快速路径。没有新增依赖、修改数据库结构、引入跨请求缓存或修改持久化数据。

工作区存在正在进行的并行修改。会话列表聚合、附件清理、搜索、关闭恢复与 Web 状态相关文件未纳入本轮写入范围；本报告不将这些并行修改计为本轮成果。

## 已完成的优化

### 1. 污染历史隔离：重复回溯改为每节点一次判定

文件：`src/limbowave/application/services/runtime_state_service.py`

原实现对每条候选消息都从自身沿父链回溯，确认它是否属于本会话的安全用户消息之后。连续长链中，相同祖先被反复访问；随后重新连接被删除的前缀时，共享前缀也会被反复遍历。

改动：
- 在单次调用内缓存节点是否属于安全会话的判定。
- 缓存移除节点对应的最近保留父节点。
- 使用迭代遍历而不是递归，避免深链触发递归深度限制。
- 未检测到污染时仍直接返回原输入。

复杂度：最坏平方级祖先遍历改为线性遍历，代价是单次调用内额外的线性空间。

保持不变：输入顺序、毫秒时间边界、配置节点、工具消息、摘要移除策略、缺失祖先处理以及原有循环检测规则。仅修改恢复副本，不修改审计记录。

### 2. 撤销压缩：共享覆盖层只解析一次

文件：`src/limbowave/application/services/compression_context.py`

原实现逐条处理保留消息，每个后继都可能重新走过同一整条压缩覆盖层链。

改动：
- 缓存覆盖层最终对应的原始父节点；共享覆盖层的后继复用结果。
- 完全没有应用压缩覆盖层时，只浅复制列表，保留原有条目对象。
- 不改变用量失效处理、原始用量记录、原生压缩节点或可达循环报错行为。

复杂度：共享祖先压力场景由 `后继数 × 覆盖层数` 降为二者之和。

### 3. 分支镜像选择：只求所需结果，不排序全部候选

文件：`src/limbowave/application/services/runtime_state_service.py`、`src/limbowave/application/branch_path.py`

- 构建指定分支快照时，单遍选择每个 entry 的最早 `(captured_at, id)` 镜像；分支顺序仍由父链决定。
- 查找镜像链尾时，先计算父节点集合，再单遍选择最新的非父节点。
- 全部排序键相等时，保留旧实现的稳定性：首次捕获取输入中第一个，链尾取输入中最后一个。
- **未删除**构建整个会话快照时确实承担时间顺序语义的排序。

最坏时间复杂度由 `O(N log N)` 降为 `O(N)`；已排序输入上的实际收益可能小于乱序样本。

## 性能基准

环境：Windows 11、Python 3.12.13。每项预热一次，3 次采样取中位数，单位毫秒。
最终复测在同一进程交替执行修改前归档函数与最终函数；构造数据不计入时间。
使用纯合成数据，不读取真实会话、资料库或网络。

| 场景 | 修改前 ms | 修改后 ms |
|---|---:|---:|
| 污染历史隔离：4,002 个节点 | 1191.206 | 5.843 |
| 共享压缩链：4,000 个覆盖层 + 4,000 个后继 + 根 | 1769.314 | 11.689 |
| 分支快照选择：4,000 个乱序镜像，恢复单节点分支 | 3.164 | 0.788 |
| 选择链尾：4,000 个乱序镜像 | 3.600 | 1.342 |
| 无覆盖层路径：4,001 个节点 | 1.549 | 0.264 |
| 无污染隔离快速路径：4,001 个节点 | 0.250 | 0.242 |

规模增长复测：

| 规模参数 N | 污染链：前 / 后 ms | 共享压缩链：前 / 后 ms |
|---:|---:|---:|
| 500 | 15.448 / 0.791 | 24.544 / 1.091 |
| 1500 | 157.421 / 2.618 | 266.565 / 3.590 |
| 4000 | 1191.206 / 5.843 | 1769.314 / 11.689 |

污染链总节点数为 N+2，共享压缩样本总节点数为 2N+1。
**压力场景刻意放大共享祖先问题，并非通常的聊天形态；不能把这些倍数等同于整个应用提速倍数。**
正常无污染路径耗时基本相同，不应将小于 0.01 ms 的差异解读为有效收益。

复测命令：
```powershell
.\.venv\Scripts\python.exe scripts/benchmark_history_recovery.py --samples 3 --sizes 500 1500 4000 --output .var/history-recovery.json
```
脚本测量当前实现；上表的修改前数据来自改动前保存的函数副本。

## 验证记录

- 新增 `tests/unit/test_history_recovery_performance.py`：18 个测试通过。
- 修改前先运行初始测试集，4 个复杂度守卫失败、9 个语义测试通过，确认测试能暴露原问题。
- 对改动前归档函数与改动后函数进行固定种子 `20261014` 的随机结构对照：隔离、撤销压缩、链尾选择、分支快照各 5,000 例，合计 **20,000 次结果/异常对照一致**。输入包括乱序、缺失父节点、循环、重复捕获及不同类型节点。此为本次一次性验证，不是仓库永久测试。
- 最终定向回归：**55 个通过**（8.15 秒），包含恢复、分支、压缩与全部新增守卫。
- 修改的 3 个生产文件通过定向 Mypy 检查（`--follow-imports=silent --no-incremental`）。
- 修改的生产文件、新测试及基准脚本通过 Ruff；生产文件差异通过空白检查。
- `tests/unit` + `tests/integration`：**2,233 个通过、7 个跳过、2 条告警**，338.12 秒。跳过项为 POSIX/符号链接/Unix socket 等当前平台不满足的条件；未新增跳过或放宽断言。两条告警为 Windows asyncio 子进程/管道对象析构时的 `I/O operation on closed pipe`，本轮不宣称全库零告警。
- 全量测试收集后补充了 2 个纯比较次数守卫；它们已在最后 55 个定向回归中验证。
- 桌面相关回归：**26 个通过**，12.07 秒，离屏运行以下 4 个文件：

- 未运行全部桌面 UI 测试、Web 前端全套测试或真正的 Linux 平台测试；没有改这些端的实现。
